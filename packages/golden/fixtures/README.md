# Pine Script Golden Test Suite

Golden datasets for TradingView **Pine Script v5 / v6**. Each case consists of a Pine source and
the native results exported by TradingView itself. It serves as the compatibility baseline for any
Pine parser, indicator engine, or backtester.

This suite contains only **data and facts**: sources, TradingView compilation results, chart
exports, strategy report exports, and the necessary market inputs captured independently. How to
compare, how to set tolerances, and which features an engine supports are left to the consumer.

---

## 1. Design principles

1. **Exports are added to the suite unchanged**: `data.csv` (Export chart data) and `report.xlsx`
   (Download data as XLSX) are both native TradingView exports, with no preprocessing or manual
   cleanup. Capture records state the account plan; when it was not independently recorded, this
   is marked as such and not presented as verified Premium. Completeness checks must still cover
   the full history and report range of the same calculation.
2. **TradingView behavior is the ground truth**: the compilation results and exported data
   recorded in `meta.json` follow TradingView's actual behavior. A suspected TradingView bug is
   only described in `notes`; the exported files are never modified.
3. **v5 and v6 are captured independently**: the v5 and v6 versions of a case are each exported
   natively under their own version, and each keeps its own copy even when the file contents happen
   to be identical.

Calendars are independent market inputs: `calendar.json` is generated by a project script from the
calendar probe's TradingView CSV, and each applicable case can store its own copy of the same
capture. The v5/v6 results of the script under test must still be captured independently.

a calendar automatically by symbol and does not search a global data directory. See
[calendar inputs](docs/calendar-inputs.md).

### Naming rules
- **The directory name is the test ID.** Directories with the same name under v5 and v6 are two
  versions of the same case.
- Prefixes:
  - `P_fmt_*` layout and formatting, `P_syn_*` full syntax coverage, `P_err_*` compile errors,
    `P_ver_*` version-difference probes;
  - `I_*` indicator and language evaluation features, `M_*` time and timezones, `A_*` constant
    numeric semantics;
  - `S_*` strategy order-matching features, `B_*` pending orders and string baselines.
- Variants of one script with different symbols or parameters are distinguished by a
  double-underscore suffix, such as `M_time__btcusdt_60` and `S_commission_slippage__pct`.
- The first effective code line of `source.pine`, `//@version=N`, must match the version of its
  directory. There are only two exceptions: `P_err_no_version` (no version declaration) and
  `P_err_version_4` (a v4 script). They are placed in the v5 directory only because every case must
  be in one of the two directories.

## 3. Case file format

Each case directory contains:

1. `source.pine`: the script under test;
2. `meta.json`: symbol, timezone, export information, compilation result (parse), and verification
   status;
3. `data.csv` (indicator / strategy): the complete bar history and all `plot*()` columns from
   TradingView's native export;
4. `report.xlsx` (strategy): the native 5-sheet export of the TradingView strategy report;
5. `calendar.json` (when needed): generated from an independent TradingView calendar probe CSV by
   `packages/golden/scripts/import-calendar.ts`; it contains sessions, weekly/monthly boundaries,
   and provenance records. See the
   [generation procedure](docs/calendar-inputs.md#generation-and-recapture).

Capture provenance, hashes of the original files, and pairing conclusions go in `meta.capture`;
the context needed for execution goes in `meta.execution`. The complete operation record and the
two CSVs exported before and after stay in a separate capture archive. No notes, manifest, audit,
or diff files are added to adopted case directories; the archive takes no part in runs.

### 3.1 `source.pine`
The source of the Pine script under test. In indicator / strategy cases, each `plot*()` call
corresponds to one column in `data.csv`, in order of appearance.

### 3.2 `data.csv` (Export chart data, unmodified)
- Column 0 `time`: bar open time as a UNIX timestamp in seconds (UTC);
- Columns 1–4 `open, high, low, close`: prices;
- `Volume` column: volume (capitalized, as exported by TradingView). The loader locates this
  column by its header. It can be column 5 or appear anywhere after it, but there can be only one;
- Remaining columns from column 5 onward: one column per `plot*()`, named after the plot title.
  Boolean values are recorded as `1/0`, and `na` is an empty cell.
- The last row can be an unclosed realtime bar whose plot columns are empty.

### 3.3 `report.xlsx` (Download data as XLSX, unmodified)
Five worksheets: `Performance`, `Trades analysis`, `Risk-adjusted performance`, `Trades`, and
`Properties`.
- In the `Trades` sheet, each trade occupies two rows (the Exit row above the Entry row).
  `Date and time` is a naive datetime in the **chart timezone** (an Excel serial number) and must
  be converted to UTC using `meta.chart_timezone`. An open trade is recorded as
  `Date and time = "Open"`, `Price = "—"`.
- The `Properties` sheet holds two-column key-value pairs that record the strategy properties and
  input settings at export time.

### 3.4 `meta.json` (schema_version 2)

```jsonc
{
  "schema_version": 2,
  "id": "S_margin",                           // = directory name
  "kind": "strategy",                         // "parse" | "indicator" | "strategy"
  "pine_version": 5,                          // matches the directory and the first line of source
  "description": "...",
  "tags": ["micro", "broker", "margin"],
  "source": { "origin": "micro", "author": "", "license": "", "url": "" },

  // parse cases only: the TradingView Pine Editor compilation result
  "expect": { "compile": "error", "error": { "line": 3 } },

  // indicator / strategy cases only
  "syminfo": {
    "tickerid": "BATS:AAPL", "ticker": "AAPL", "prefix": "BATS",
    "type": "stock", "currency": "USD", "basecurrency": "",
    "timezone": "America/New_York",           // exchange timezone
    "mintick": 0.01, "pricescale": 100, "minmove": 1, "pointvalue": 1,
    "mincontract": 1,                         // minimum contract quantity (can be fractional for crypto)
    "session": "regular",                     // regular | extended
    "session_hours": "0930-1600",
    "description": "Apple Inc."
  },
  "timeframe": "60",                          // TradingView timeframe notation: "60", "D"
  "chart_timezone": "America/Los_Angeles",    // chart timezone at export (basis for XLSX timestamps)
  "data": {
    "file": "data.csv",
    "time_format": "unix_seconds",
    "exported_at": "2026-09-04T06:57:29Z",
    "plan": "Premium",
    "tv_release_month": "2026-09",
    "columns": ["time", "open", "high", "low", "close", "Volume", "..."]
  },
  "report": { "file": "report.xlsx", "exported_at": "2026-09-04T06:57:36Z" },   // strategy only
  "session_calendar": { "file": "calendar.json" }, // optional; the file is in this case directory
  "inputs": {},                               // input values overridden at export; empty means defaults

  "verified": true,                           // whether checked against actual TradingView output
  "notes": ""
}
```

`verified: false` means the case is not yet part of the passing regression gate. The provenance
may still need confirmation, or a confirmed native result may still disagree with the engine. See
`notes` and [known issues](docs/known-issues.md) for the specific reason.

Without a `session_calendar` declaration, no calendar is passed to the engine; once it is declared,
a missing file or an invalid format fails loading. Both the calendar file and the declaration are
part of the fixture fingerprint. See [calendar inputs](docs/calendar-inputs.md) for provenance,
format, and capture method.

The optional `execution` records a Replay selection boundary confirmed by an independent capture:

```json
{
  "mode": "replay-selection",
  "selected_at": "2026-09-04T00:00:00Z",
  "paused": true,
  "stepped": false
}
```

Minute timeframes require the last market bar to end exactly at the selection time. `W` / `1W`
with an explicit UTC timezone is also supported: every market bar opens on Monday at 00:00 UTC,
and the selection time is exactly one week after the final bar's open. Both apply only to strategy
captures that independently recorded the selection time and paused state.
Fill in `stepped` only when it has been confirmed whether Replay was stepped forward. Older
records that do not state it can omit it; it must not be backfilled as `false`.
`stepped: true` is not currently supported. The execution context comes directly from metadata;
notes in the archive are not read. It means that, at this selection boundary, the regular strategy
close calculation for the final bar has not yet run; Replay is not treated as realtime.
All OHLCV is kept; unknown barstate and extra tick/fill/on-close modes are reported explicitly as
unsupported. Inputs come from the capture context and market times; they are not inferred from
empty plots or expected indicator values. See the
[compatibility notes](../../../docs/COMPATIBILITY_NOTES.md) for details.

The optional `capture` keeps a brief provenance record, such as the SHA-256 of the original files
in `files`, the CSV → XLSX → CSV export times and byte-for-byte pairing result in
`paired_exports`, the origin of independent market inputs, and the archive location. It does not
replace `syminfo`, `inputs`, `settings`, or `execution`, and engine inputs are not derived from
provenance text.
