# Calendar inputs

`calendar.json` is generated by a project script from the CSV that TradingView exports for an
independent calendar probe. TradingView exports CSV; JSON is this project's market input format.
A golden case that needs it stores the complete file in its own directory and declares it in
`meta.json`:

```json
{
  "session_calendar": { "file": "calendar.json" }
}
```

The file path is relative to the case directory. Without a declaration, no calendar is passed; a
declared file that is missing or invalid fails loading. The loader does not match calendars by
symbol and does not access a global directory. The file and the declaration are part of the fixture
fingerprint. Each case directory contains all market inputs needed to reproduce its execution.

The calendar file keeps the importer's `schemaVersion: 1` format: `provenance` records the source,
and `calendar` contains the coverage range `from` / `to` in Unix seconds, the sessions `sessions`
(`open`, `close`, `tradingDay`), and optional weekly/monthly `periods`. The harness passes only
`calendar` to the engine's `sessionCalendar` parameter. Each engine run has isolated state; the
engine does not read files or look up internal market data.

The calendar serves session-dependent rules such as time functions, default VWAP resets, and the
daily fill limit. A missing session inside the complete coverage range denotes a known market
closure. Outside the range, no data is available, and the fixed session and timezone rules passed
in still apply. Weekly/monthly boundaries have their own coverage ranges. Holidays, early closes,
and provider boundaries must not be derived from missing price rows or expected plots.

## Current capture source

The AAPL calendar in the cases comes from an independent TradingView metadata probe, captured on
2026-09-09 on a `BATS:AAPL` regular-session daily chart. It was exported after loading the
complete history with **Go to date → 1980-12-12** and contains 11,520 sessions through
2026-09-08. Only the probe's seven named fields are used; columns from other studies in the raw
CSV are ignored. No prices, expected indicator values, trade records, or report metrics were used
to generate the calendar.

The `calendar.json` files in the current 8 cases are byte-for-byte identical copies of this single
capture and conversion. They are used by the v5/v6 `I_volume`, `M_time__aapl_60`,
`M_time__aapl_D`, and `S_risk_max_intraday_filled_orders` cases. The calendar was captured by an
independent v6 probe and serves as a market input for the tests in both versions. This does not
mean 8 captures were made, and it does not replace the separate native results of the v5/v6
scripts under test.

This data records the provider's historical metadata at the time of capture. Some older early
closes are not recorded, and weekly holiday anchors also differ historically. The engine does not
hard-code dates or derive correction rules from golden expected values. Independent weekly/monthly
time boundaries preserve these measured behaviors.

The JSON `provenance` keeps the chart, capture time, probe, and SHA-256 of the raw export.
`tests/calendars/tradingview-aapl.json` in historical manifests (later moved to
`data/calendars/`) now corresponds to the byte-identical `calendar.json` in each case.
`provenance.probe: "probe.pine"` corresponds to
[packages/golden/scripts/probes/calendar.pine](../../scripts/probes/calendar.pine).
The original manifests and provenance fields are preserved and are not rewritten because of
directory moves.

## Generation and recapture

1. Run [calendar.pine](../../scripts/probes/calendar.pine) on a separate regular-session daily
   chart, confirm that it compiles and executes, and load the complete history.
2. Use TradingView's **Export chart data** and export CSV with Unix timestamps. Keep the raw file,
   the exact probe, and the environment record.
3. From the project root, run [import-calendar.ts](../../scripts/import-calendar.ts) to convert
   the native CSV into calendar JSON:

```sh
npm run build
node packages/golden/scripts/import-calendar.ts <download.csv> <calendar.json> America/New_York <UTC-export-time> <chart-url>
```

The probe columns correspond to JSON fields as follows:

| CSV probe column | Pine expression | JSON content |
|---|---|---|
| `session_open` / `session_close` | `time` / `time_close` | `sessions[].open` / `close` |
| `session_trading_day` | `time_tradingday` | `sessions[].tradingDay`, formatted as `YYYY-MM-DD` |
| `calendar_week_open` / `calendar_week_close` | `time("W")` / `time_close("W")` | `periods["1W"][].open` / `close` |
| `calendar_month_open` / `calendar_month_close` | `time("M")` / `time_close("M")` | `periods["1M"][].open` / `close` |

The CSV chart time column can use Unix seconds, but these seven Pine output columns remain in
milliseconds. The importer converts them to seconds and merges duplicate weekly/monthly records.
Coverage runs from the first session's open to midnight of the day after the last session's open
date. The weekly/monthly `from` / `to` lookup ranges are generated in the specified exchange
timezone, while `open` / `close` keep the endpoints observed by the probe. The JSON also records
the chart link, export time, probe name, and SHA-256 of the raw CSV, so the conversion can be
traced to its source.

The importer applies to regular-session daily exports. The probe's early-close display table does
not affect the exported fields. The engine interface also accepts independently supplied sessions
that span midnight; this does not mean the current daily importer has captured other markets or
sessions.

After confirming the provenance, market, timezone, session, and coverage, place the complete JSON
in each case that needs it, declare it explicitly, and run the full regression suite. A calendar
change is a fixture input change; it needs an explanation and a baseline migration. Native expected
data, tolerances, or scoring rules must not be modified to fit the calendar.
